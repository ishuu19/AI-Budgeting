# Life OS changelog

Newest first. Add an entry for every change that touches the assistant, data model or roadmap. Keep each line to what changed and why.

## 2026-10-23

- **Fix: wrong year heading on Achievements.** The stored dates were right (phone and cloud). The year heading was read when the row was drawn, after the loop that builds the list had ended, so every heading showed the last year in the list. The heading now keeps its own value. Birthdays and Trips use the same list layout and were checked: only Achievements had it.

- **Why nothing uploaded, and the fix.** Two causes. (1) The server refuses a batch whose rows have different keys (HTTP 400, PGRST102). The sync DTOs leave out empty fields, so one empty field in a calendar event, reminder, media or wish row failed that table; sync treats any failed step as a failed run and keeps the cursor, so nothing after it ever moved. `UniformKeysInterceptor` now splits such a batch into one request per set of keys, for every table (tested). (2) A failed run waits in retry back-off that grows to hours, and `syncNow` used KEEP, so every later trigger (new data, network back) was dropped. `syncNow` now uses REPLACE with a short linear back-off, and opening the app also starts a sync. A failing step is now logged with its error type and place. Seen on the test phone: all tables answered 2xx, the cursor moved for the first time since 02:16, and the achievement and both wishes were sent (HTTP 200). Changes already trigger an upload 4 seconds later, when the network returns, and every 15 minutes.
- **A sign-in lasts 30 days.** The app stores when you really signed in (a token renewal does not reset it). At 30 days, checked every time the app opens and before every token refresh, it logs out and the sign-in screen shows; local data is kept for upload after the next sign-in (`sessionTooOld`, tested). A refused refresh token still logs out at once. The length of the access token itself (Supabase "JWT expiry", about an hour by default) is a server setting that the app cannot change; the app renews it silently inside the 30 days.
- **Wish upload fix.** Batch uploads of wishes got HTTP 400 because rows with an empty field were sent with fewer keys than others (PostgREST needs equal keys). Uploads now send nulls, which also lets a cleared field clear on the server. Seen in the phone log: birthdays uploaded (22 rows, HTTP 201); the wishes batch was refused, then both wishes went through when retried row by row (HTTP 200). The sync cursor had not moved yet when last checked, so the last step of that run is unconfirmed.
- **A dead sign-in logs you out.** When Supabase refuses the refresh token ("Invalid Refresh Token", "Already Used", HTTP 400 to 403), the app clears the session and the sign-in screen shows. Local data is kept and marked as waiting to upload, so signing in to the same account sends it up. No network or a server error does not log out. The classification is `isSessionDead` (tested). Sign-in stays Google; the fingerprint lock still guards opening the app.
- **The chat can edit every field of an entry.** Edit actions now cover all stored fields: jobs (url, source, applied date, other dates), pantry items (name, category, quantity, unit, location, expiry, kind), shopping lines (name, quantity), garments (name, type, colors, seasons, laundry), birthdays (name, date, year, note, time of day, each reminder), trips (reminders), wishes (link, wanted-by month), notes (title, whole text, tags, place), tasks and events (end, all-day, links), transactions (type, place, currency, recurring), bills (category, note, place, currency) and debts (person, direction, dates, phone, email, place, currency, paid). New repository methods `updateItem`, `updateLine`, `updateGarment`. The context shows every one of these fields so the AI sees current values. Not editable by chat on purpose: ids, owner, visibility, source links, photos.
- **Cloud upload check (wishes and the other life records).** The server tables exist and answer. Two defects found and fixed: (1) `RowSync` ignored a server refusal (HTTP 4xx) and swallowed every error, so a refused row was dropped and the sync cursor moved past it; it now retries row by row, logs a refused row, and rethrows other errors so the cursor stays and the run is retried. (2) Chat-made wishes and achievements could exceed the server's length checks (note 1000, link 2000, amount at least 0, wanted-by `yyyy-MM`); the actions now cap to those limits.
- **Sync was stopped by a dead sign-in.** On the test phone nothing had uploaded since 02:16 because the refresh token was "Already Used". Cause: the Supabase client's own background refresh and the app's refresh both rotated the token, and app callers could refresh at the same time. Now the plugin's auto refresh and storage are off, and `refreshIfNeeded` runs under a lock. An already-dead token cannot be revived: the user must sign in again once.
- Not verified: no row could be read back from the server (needs the user's sign-in), so upload is confirmed only by code and the refresh log, not by seeing rows in the cloud.

- **Home is the chat; the mic only opens the mic.** The Home tab now opens the chat (briefing on top, then the conversation and ask bar) instead of the separate briefing page. The centre mic no longer navigates: on Home it starts listening in the chat; on any other screen it opens the phone's speech dialog over the current screen, and the words go to the Home chat once heard. The ask-bar mic does the same. The old `BriefScreen` route is no longer reachable (left in place, unused). Spoken language in the phone dialog follows the phone, not the in-app voice-language setting. Not run on a device.

- **Chat questions: counts, notes, app time, typos.** Key words never leave the AI with an empty view: when a word matches nothing ("notes", "list"), the whole section is shown and says so, and a filtered section always says "N of M match". Typos of one letter still match ("siam" finds Sam). A question about a note searches note text on the phone and sends only a short snippet per hit. Wishes now come with this month's income and spending so "most feasible" can be answered. **App time is now readable by the assistant** (a change from "never read"): only the top apps by screen time for today, 7 and 30 days, and only when the question needs it. A plain-text or action-less answer from the model is accepted as the answer instead of an error. Anything about a password or PIN still goes to the Passwords card; the AI never sees it. The router prompt now has examples for these questions.

- **Search and chat questions: key words first, then only those sections.** The router now also returns key words (names, items, merchants) next to the record kinds. The assistant sends only records that mention a key word; people include their memories, tasks and events also look at past ones, and transactions look through all of them, not just the newest 30. A general question ("what is on today") has no key words and gets the normal view. In global Search, a sentence that finds nothing as typed is sent to the AI once (`SearchKeywords`, typed text only, no records) to pick key words and kinds; the app then searches just those kinds, and a line shows what the AI looked for.
- **Type it, and AI files it, in every Library section.** People, Jobs, Pantry (and its shopping list), Wardrobe, Birthdays, Trips, Achievements, Wishes and the Vault (notes) each show an AI bar at the top. One sentence adds, changes or removes records in that section, or answers a question about it. The bar can only use its own section's actions. Not covered on purpose: Passwords (never typed to an AI), Household, Life log and App time.
- **Home chat answers about everything and can change it.** The router gets a `data` route. A question about the user's own data, a Library change, or an edit, complete or delete of an existing transaction, bill, debt, task or event goes to the assistant with all records as context; new expenses, bills, debts, reminders and events still go through the voice cards. Answers come only from the supplied records and say "I don't know" when a record isn't there.
- **Risk tiers.** Adding a private record is LOW and applies at once with Undo. Edits, removals, tasks and events are MEDIUM and wait for a tap. Anything that changes a transaction, bill or debt is HIGH and waits for a tap. A step shows "done" only after the executor applied it. An edit or delete naming a record that is gone is rejected, not offered. The model's own risk claim is ignored.
- **New code.** `LibraryActions` (41 `lib.<area>.<verb>` actions), `AssistantContext` (one line per record with its id), `LibraryAssistant` (plan, execute, approve, skip, undo), `AssistantTurnCard`, `LibraryAiBar`. `ActionSpec` gained an optional `preview`; `Orchestrator.plan` gained `allowed` and `answers`. No Room or Supabase change.
- **Privacy.** The model sees record names and short fields. Note bodies are never sent (titles only), passwords and locked Vault folders are never read, and the signed-in user id is stamped on every action by the app, not taken from the model. The assistant calls the fast model through `AiGateway` (`ai-proxy` first), like the other asks. The proxy keeps 4000 characters of system text and 8000 of user text, so the router also names the one to three record kinds a question is about, only those are sent, each is cut to fit, and the message goes last. If the router names none, all kinds are tried and the tail of the action list may be cut.
- **Not verified.** Compiled, Hilt graph built, unit tests pass (assistant, args, context text, route parsing). Not run on a device, so model quality for routing and for picking the right record id is unmeasured. Edits to wardrobe items and to a pantry item's name are not offered (the repositories have no update). Marking a wish bought still happens in the app because it creates a transaction.
- **Gaps.** The section bars have no mic yet; the Home mic goes through the same chat route. Goals, budgets, subscriptions, receipts and memories beyond three per person are not in the context yet.

### AI-first redesign
- **Photo bug fixed.** "Couldn't read that photo" came from treating the null that a bounds-only `BitmapFactory` decode returns as a failure. Photos now save.
- **Photo analysis no longer waits for the upload login.** `CaptureWorker` runs analysis first; only the R2 upload needs a fresh Supabase session. A phone whose refresh token is dead ("Already Used") now still gets photos named and filed; only the backup waits for a new sign-in.
- Photo reading uses `gemini-flash-latest` (the old `gemini-2.0-flash` returned 404), in the app and in `ai-proxy` (redeployed).
- **New layout around "say or snap, the AI does it".** Bottom tabs are Today, Plan, Capture, Money, Life. Settings moved behind a gear on Today. The old "You" list is gone: Pantry, Wardrobe, People and Home live in the new **Life** tab; Subscriptions moved into Money Overview; Money Overview is one main figure plus tiles.
- **Today is the AI front door.** The voice/photo/text composer sits at the top of Today, with a "Needs your OK" queue under it for anything the AI could not finish (a name to confirm, a subscription to track).
- **Manual is the backup.** "Add manually" under every composer opens one sheet: expense, task, event, note, pantry item, clothes, person.
- Appearance setting (System / Light / Dark); window background and splash follow the theme; floating tab bar.

### Capture decisions
- Split storage by data type (user decision): text data in Supabase (Postgres + RLS), files in Cloudflare R2 (S3-compatible, no egress fees). Access control for files is the Edge Function, which builds the key from the verified user id.
- Capture filing goes through `Executor` with registered `capture.*` actions (`CaptureActions`). Garment, food, receipt draft and person are LOW; `capture.track_subscription` is MEDIUM and runs only on the user's tap. The input ref is the photo id, so a retried worker cannot file twice, and every step lands in `assistant_actions`.
- `media_assets` now syncs (`MediaAssetExtraSync`); `019_media.sql` is applied to the live project (RLS on, 4 policies) with its own copy of `touch_row_updated_at()`. NOTE: the live project only has migrations 001-003; 004-011 (calendar, plans, habits, jobs, voice history, ...) are not applied, so sync for those tables cannot work until they are.
- Outfit asks add current weather (Open-Meteo) from the last stored location when it is under 24 h old; otherwise weather is omitted, never guessed.

### Decisions
- Evolve the existing Android app (ADR 0001).
- Reuse the existing voice pipeline (parse → confirm card → save → undo → history) instead of building a second one. The fast model returns the same `items` JSON the older cloud path used, so cards, history and undo work unchanged.
- Default model chosen by test, not by name. Same 4-item message: `gemini-3.1-flash-lite` ≈ 1.7 s and correct; `claude-haiku-5.5` ≈ 3.8 s with output cut off at 600 tokens.

### Verified
- Full unit suite: 394 tests, 0 failures.
- Live OpenRouter call with the real voice prompt: a three-item message (expense, reminder with date, debt) returned correct items in ~2.6 s; an ambiguous message returned amount `null` instead of a guess.

### Not verified
- Not run on a device or emulator. The voice screen itself was not exercised.
- Cost and latency over a real session.

### Known limits
- `preferLocalKinds` still lets rules override the AI when the words clearly name a bill, debt, goal or budget. Kept on purpose until the fast prompt carries the bill and debt fields; revisit with real transcripts.
- The OpenRouter key is compiled into **debug** builds only. Release fast-model calls go through `ai-proxy`; a release build does not send a client provider key.
- `Orchestrator` and `Executor` are injectable, and a low-risk plan can be executed through them. The voice screen still uses confirm cards and does not call them yet. The action registry is empty until feature packages contribute specs. `assistant_actions` / `event_log` sync is not bound, and `012` stays in `supabase/planned/`.
